# DEV-838: threaded refresh work

Baseline: `d01da09e26adf76ef8fe60e2a5f76226426a167b`.

The folder CTE previously materialized entire email rows, including full bodies
and MIME metadata, and copied them through a window sort. The cross-folder CTE
also materialized entire messages despite only needing grouping/statistics fields.
The new projections retain a 300-character body prefix for folder rows and only
small statistics fields for cross-folder rows. Grouping, count queries, order,
window partitions, joins, and pagination are unchanged. No migration or cache.

The REST threaded list now makes one `getThreadedEmailPage` RPC. Its two SQL read
paths execute synchronously before either promise is awaited. This removes the
second RPC and the opportunity for an arrival/move to interleave between those
reads. Polling stays at 30 seconds. The non-threaded route is unchanged. Search
of source callers found no direct uses of these threaded readers in the MCP,
agent, or IMAP surfaces; their mutations are reflected by the uncached SQL reads.

## Regression evidence

`test/fixtures/threaded-baseline.json` freezes the four baseline SQL statements,
including the expanded subject-normalization expression. The test does not
regenerate this oracle from the implementation. `test/threaded-query.test.ts`
compares complete responses against it using workerd and real local DO SQLite.
The small fixture exercises the actual REST handler and R2 mailbox registry,
thread IDs, changing/shared subjects, legacy subjects, empty/null subjects,
reply/new drafts, cross-folder participants/read counts/draft state, tied dates,
Unicode snippets, deep/out-of-range pages, unknown/empty folders, folder name
lookup, and reads immediately after arrival, mark-read/thread-read, draft
creation/update/deletion and move. No external email or AI call is made.

The 1k/10k fixture compares full responses for inbox and draft pages 1 and 10.
It has five-message subject groups, explicit thread IDs except every 13th row,
seven senders, alternating read state, 10% drafts, 20% sent and 70% inbox,
unique increasing dates, reply parents every third row and 10KB bodies.

Existing quirks are intentionally retained: empty legacy subjects can produce
a different list grouping from the count; a thread spanning subjects can
multiply rows in the conversation mapping; date ties lack a secondary ordering.
This refactor does not redefine those contracts.

## Reproduce the performance measurement

Use Node 24: `node scripts/benchmark-threaded.mjs`.
The script extracts the current SQL directly from the source, compares results
with the frozen baseline, and measures the complete list-plus-count pair.
Setup is excluded. Each case has one warmup pair and nine measured pairs with
alternating execution order. The output includes every sample, median, maximum,
SQLite/Node versions and EXPLAIN QUERY PLAN for both list implementations.

`dev-838-benchmark.json` is the captured output. This is an in-memory Node SQLite
microbenchmark with the relevant email columns and query indexes, rather than
a hosted workerd latency measurement. Real DO correctness is checked separately.
The baseline carries fewer metadata columns here than it does in production.
The RPC saving is not included. Large bodies are intentional and disclosed;
mailboxes with small bodies will benefit less. These numbers are neither a
production latency promise nor evidence of lower Cloudflare billing.

## Remaining limits

The algorithm still computes folder conversation mappings and whole-mailbox
cross-folder statistics/windows, and the count still performs separate grouping.
Offset pagination still processes earlier groups. This change reduces repeated
materialization/sort payload and RPC overhead; it does not eliminate mailbox-size
scaling. Page-first enrichment or shared grouping can be evaluated later against
this oracle, especially around the legacy mapping/count quirks.

## Dependency repair

Fresh `npm ci` failed because the lock lacked the vitest workers pool's optional
workers-types peer. The lock-only repair adds that nested peer entry; existing
package versions and unrelated lock metadata are retained.
